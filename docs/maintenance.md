# 发布后的维护闭环

维护者：qzqzqz。工程协作者负责脱敏复现、回归测试和候选验证；维护者批准正式发布及授权事项。此为维护流程，不表示首版已发布或首周跟进已完成。

## 分流和优先级

| 类别 | 处理 |
| --- | --- |
| P0：数据/凭据泄漏、数据损坏、未经授权重复付费 | 先限制受影响路径和保存证据，私密处理；评估撤回发行物与用户告知。不能继续普通迭代 |
| P1：无法安装、主要路径阻断、关键事实错误、停止唤醒失效 | 复现后补回归测试，优先修复并验证补丁；新版本发布前必须闭合 |
| P2：非阻断表现、文案、可选路径局限 | 记录影响和绕行方式，按周集中评估；不以其为由无限扩大当前范围 |
| 新功能建议 | 单独积压，不混入稳定性修复 |

GitHub 标签准备：install、monitoring、quality、agent、windows、macos、needs-info、confirmed、fixed、P0、P1、P2。标签尚未远程创建；在对应权限获准后操作。不给所有缺陷都打最高优先级。

## 每条缺陷的闭环

1. 查重并收集版本、平台、脱敏步骤；安全内容移往私密沟通，公开内容不复制扩散。
2. 在隔离环境用合成/公开材料复现。先记录失败用例；结果不明不自动重试，不绕过付费保护。
3. 确定影响版本、优先级与负责人；信息不足标记 needs-info，未复现不能直接宣称已修。
4. 最小修复 + 回归测试，复核相邻路径与平台差异，PR 说明数据迁移和风险。
5. CI、安装态验证、相关目标平台验证通过；实际模型行为改变时单独安排有预算授权的真实复验。
6. 固定补丁版本、源码和资产哈希，维护者确认后发布；不能覆盖原版本资产。
7. Release notes 链接已修复问题，通知报告者按安全升级说明复验，确认解决后关闭；标记 fixed 不等于已交付。

## 节奏和指标

首周内部安排每日整理反馈一次，之后每周整理一次；没有反馈不能推断全部用户成功。这不是对外响应 SLA，不承诺未落实的 24 小时支持。

按版本记录：独立首次建档成功/失败与样本量、安装/升级失败、核心闭环阻断、关键事实错误、unknown 与恢复情况、复发问题。只统计主动提供且已脱敏的信息，不自动收集使用数据。不同版本和缺失数据不混算百分比。

## 补丁、回滚和撤回

- 补丁沿用稳定分支，只修明确问题；提供源/依赖/资产对应关系、影响范围、用户行动和已知问题。
- 升级前正常退出并备份；未知请求及授权记录必须保留。回滚需要数据库兼容证明，或恢复与旧程序成对的备份到隔离目录验证后再由用户确认切换。
- 不得只替换旧程序并直接读取迁移后的唯一数据库，不得把旧备份恢复到活动数据目录覆盖当前数据。
- 严重安全或数据问题需要维护者决定撤回下载资产/暂停推广，公开安全说明避免暴露利用细节；保留审计记录，不把问题隐藏为静默改包。
- 凭据已泄漏须撤销/轮换；补丁不能代替这一步。
