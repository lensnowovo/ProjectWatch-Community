# Windows 构建缓存与手动小更新

完整安装器继续用于首次安装、离线安装和恢复。小更新是另外生成的 ZIP，必须对应一个精确的已安装版本；它不会检查网络、自动下载或自动安装，也不会启动监控或重试请求。

## 使用者

只有官方发布说明明确列出的对应小更新包才适用。核对发布页的 ZIP SHA-256，解压到**程序和数据目录之外的新文件夹**，从托盘正常退出 ProjectWatch，再双击 `Apply-Update.cmd`。核对显示的安装目录后输入 `UPDATE` 确认。SHA-256 能核对文件完整性，但不代替可信下载渠道或代码签名。

升级会核对旧版本清单、全部程序及共享运行时文件，备份数据，然后在新版本目录组装并校验文件，最后切换启动指针。配置、数据库、暂停状态和历史请求记录不被改写。不会自动重新启动应用；成功后可使用原快捷方式打开。

以下情况会停止更新并保留旧版本：基础版本不匹配、用户改过或添加了程序文件、文件损坏、应用仍在运行、备份或文件写入失败。不要删除自定义代码或原数据来强行通过检查；保留控制台结果及失败暂存目录，使用对应的完整安装器或请维护者处理。小更新也需要足够磁盘空间，包含新版本副本和数据备份所需空间。

旧程序和备份会保留。**运行新版后若发生数据库迁移，不能只切回旧程序来回退**，需要同时恢复经过验证的匹配数据副本。小更新不更新开始菜单、卸载程序或 Windows“已安装的应用”的登记信息；这些仍由完整安装器管理。应用实际运行版本由安装状态和目标版本文件决定。

## 构建者

在现有 `python -m scripts.build_windows_bundle ...` 命令末尾增加：

```powershell
--cache-dir <仓库外的构建缓存目录>
```

缓存键包含 Python/平台、依赖 wheel 的精确哈希、pip、构建解释器和构建辅助代码。产品 wheel 不进入依赖缓存键；只改前端或产品代码时重新安装产品 wheel，复用已校验的 Python 依赖。依赖变化产生新缓存条目。命中时重新核对文件清单及哈希，复制到新目录；不使用可共同修改的硬链接。损坏缓存停止构建，保留现场。

DSH 使用原有 `prepare_dsh_runtime.py` 生成的已审核目录；其锁文件和内容未变时可继续复用，不必每次执行 `npm ci`。**完整安装器仍然包含全部依赖**，因此组装、校验、压缩和上传完整包仍有成本。缓存减少重复安装工作，不代表省略发行验证。

从两个完整、已验证的 bundle 生成手动小更新：

```powershell
python -m scripts.build_windows_update --base <旧bundle目录> --target <新bundle目录> --out <新ZIP路径>
```

构建器只输出变化或新增的应用/Python 依赖文件。它比较两份清单，只读取并核对需要传输的文件，不再次扫描两套未变化的依赖；完整候选验证仍须单独完成。安装时会完整校验旧版本和组装后的新版本。未变的 DSH、Node 不放入 ZIP；共享运行时本身变化时携带该运行时的完整新组件。删除的文件不会进入新版本，旧版本文件仍保留。Python 版本或启动器源码改变、降级时拒绝生成小包，需按完整安装器迁移路径处理。

小包包含目标清单、变化文件及离线维护脚本。`update.json` 的 `base`、`target` 是两份 bundle 清单的 SHA-256，不是仅比较版本名称。生成命令返回包大小和 SHA-256；发布时应与对应完整安装器一起列明，并保留第三方许可、源码提供和版本对应核对。

局部修改先跑缓存、更新和安装事务测试。冻结候选后集中做安装版验证、扫描和发行检查；不要每改一行就重建和上传完整安装器。小包不能绕过这些最终门槛。

## 当前边界

- 本实现针对 Windows；macOS 更新方式不在此改动中。
- 不提供自动安装、二进制差分、在线依赖下载或自定义代码合并。
- 新安装与修改过程序的用户继续使用完整安装器或源码工作流。
- 小包的启动入口使用旧安装中的 Python；旧 Python 本身损坏时须恢复完整安装。
- ZIP 尚须经过相应发行审核才可上传，代码和本地演练不等于公开发布。
