# 核心重写开发计划

2026-11-01。依据 `2026-11-01-core-rewrite.md`（方向已由用户确认）。分支 `claude/core-rewrite`，开发者 Claude。

## 0. 目标与工作规则

**里程碑（只认这两条）**
1. 已有项目点一次"更新"，相关论文/专利出现在页面并可追溯到原文。
2. 新建项目完整走到：档案与投资假设 → 监控方案 → 采集 → 分析（含预警）→ 方案复盘 → 今日动态 → 周报。

**工作规则**
- 只在本分支开发；里程碑前不碰用户真实实例，不发起真实付费调用。
- 历史数据只读：来源、证据、分析、请求回执（含 unknown）、累计费用都不改、不删、不重发。
- 不在旧路径上加准入或例外；放行一律通过派发检查与账本规则。
- 每个阶段至少一个提交，附：改了什么、跑了哪些测试、哪些没验证。
- 开发期门禁：快速测试层 + 回放测试。里程碑时：完整测试、构建、安装冒烟、完整审查、真实验收。

## 2. P1 录制—回放与快速测试层

**目的**：让真实世界的问题能在离线环境零成本、无限次复现；让每次改动几分钟内得到可信反馈。

1. **回放传输层**（新 `studio/replay.py`）
   - 在唯一注入点 `Pipeline.http_factory` 外包一层：`record` 模式保存每次请求/响应；`replay` 模式按请求匹配返回已存响应，未命中则报错（不访问网络）。
   - 匹配键：方法 + 规范化 URL（去掉 key 类参数）+ 请求体摘要；模型请求按"任务类型 + 输入摘要"匹配。
   - 敏感信息：请求头中的密钥、URL 中的 key 参数在保存前剔除。
2. **回放语料**
   - 从**备份的只读副本**（不碰正在运行的实例）读取 `studio_job_calls` 已存的完整响应，导出为回放语料；覆盖已有项目与新项目的真实来源响应和模型响应。
   - 语料存放在仓库外的私有目录，永不进入 Git。
   - 仓库内只提交：合成夹具，以及经裁剪的公开提供方响应（沿用发布检查中已有的公开夹具规则）。
3. **提供方契约测试**
   - 对每个来源适配器（新闻搜索、OpenAlex、Europe PMC、专利页面、临床试验等）至少一个真实形状的公开响应夹具，防止再出现"测试全绿、实页失败"。
4. **快速测试层**
   - 增加 `fast` 测试集（标记或清单），覆盖账本、派发、采集计划、入库、快照、分析校验、报告投影；目标 5 分钟内跑完，作为每次提交的门禁。
   - 慢测试（安装、原生运行时、全量）只在里程碑运行。
5. **既有红灯**
   - `test_collection_history` 的 `5 == 3` 与分层检查的 17 个未登记模块：查明并修正或明确登记，红灯清零。

**完成标准**：能用一条命令把某个真实项目的一次历史运行离线重放到隔离数据目录；快速层 < 5 分钟且全绿。
**确认节点**：给你演示一次离线重放（数据只在本机、私有目录）。

## 3. P2 账本派发检查与旧任务归档

1. **派发检查**（`studio/execution.py`）
   - 新增唯一函数 `dispatch_check`：在 `JobExecution.call` 同一事务内检查项目启用/未暂停/已同意、预算剩余（未知与已收到的 5xx 按全额计入）。
   - 同一请求键：成功 → 本地回放；结果不明 → 不发送，返回"未知、未重发"；失败 → 按现有可重试分类。
   - 删除跨任务阻断：`guard_legacy_model_dispatch` 的跨任务部分、刷新入口的项目级拦截；`material_ownership.project_guard` 不再被新路径调用（待 P6 删除）。
2. **预算**
   - 采用 `research_budget` 的费用合同作为每项目、每周期的总额来源；没有合同的项目使用按次数的默认额度。
3. **`archived` 终态与迁移**
   - 任务状态新增 `archived`（附原因）；迁移把所有未结束的旧任务标为 `archived`，不改请求行。
   - 队列 `claim` 不再领取 `archived`；任务页把它显示为"已归档（旧流程）"。
   - 迁移可重复执行、可回滚（只改状态列）。

**完成标准**：隔离库中——旧 unknown 键再次请求时不发送且计费不变；其他任务不被阻断；迁移前后请求表、证据表逐行一致。

## 4. P3 确定性采集任务

1. 新任务类型 `collect`（新 `studio/collect_job.py`），由"更新"按钮和定时调度创建。
2. 计划：复用 `collection_scope` / `collection_plan`，输入为冻结的确认名（含曾用名、英文名优先于英文索引）、产品名、监控方案各项的查询、来源选择。
3. 执行：复用 `CollectionSources` 适配器与解析器；单个来源失败只记该来源回执。
4. 页面补读：按规则读每类来源排名靠前的若干条正文，有页数上限（复用 `collection_pages`）。
5. 入库：每条结果到达即入库（复用 `collection_ingest`），在材料/候选页立即可见。
6. 结束：写采集批次结果（complete / partial / failed），自动排入 `analyze`。
7. 查询词提议（可选，1 次结构化调用）放到 P4b，与探索额度一起做。

**完成标准**（回放语料）：已有项目的确认名查询直接发出；论文/专利结果入库且可见；单源失败不影响其他来源；重跑不重复成功请求。

## 5. P4 快照与分析

1. 快照：复用 `material_snapshot`；采集批次结束时对有效材料建立不可变清单。
2. **相关性审核**：结构化调用，约 20 条一批，逐条判"确认相关 / 候选 / 不相关"并给依据，结果写回来源记录。替换 `dsh_record_review` 的智能体角色。
3. **事实抽取**：对确认相关材料分批结构化抽取（事件、产品、试验、专利、人员等）及原文位置。替换 `dsh_extraction`。
4. **分栏分析**：复用 `section_analysis` 的五栏与证据校验；各栏独立发布，一栏失败不影响其他栏。
5. **预警分析**：作为一个栏目，对照投资假设阅读本轮新材料（假设本身在 P4b 提取；P4 先用现有档案与研究问题作为输入，P4b 接入）。
6. **事件**：作为分析产物发布，不再是分析的前提。
7. 新任务类型 `analyze`（新 `studio/analyze_job.py`）；失败后对同一快照重排即为重做。
8. 所有模型调用经 `llm.LLM.json` 与同一账本，不使用 DSH。

**完成标准**（回放语料）：完整分析产出；人为让一栏失败，其他栏照常发布；分析失败后重做，采集调用 0，已成功模型请求回放。
**确认节点**：在本机隔离实例（独立端口、独立数据目录）上，用回放数据给你看完整的项目页和分析结果。

## 6. P4b 投资假设、方案复盘与探索

1. **投资假设**：建档时从 BP 与公开资料提取关键假设，带依据存储（新表，带版本）；用户可编辑；用户改过的条目 AI 只能提建议。
2. **方案复盘**（新 `studio/scope_review.py`，替换 `scope_maintenance` 的智能体角色）：读档案、假设、本轮分析与材料，以结构化输出提出新增/调整/移出；每项须带依据、查询词、信号标准、关联假设、退出条件。
   - 通过校验且在每轮上限内的修订自动生效于下一轮采集；其余进入现有"待你确认的建议"。
   - 写入沿用 `monitoring_plan` 的 `propose` 与条目结构。
3. **探索额度**：每轮少量查询由 AI 自由提出（与查询词提议合并为一次结构化调用）；有价值的结果在复盘中正式纳入方案。
4. **跟踪问题评估**：`question_assessment` 改为结构化直接调用，沿用 `QuestionLedger`。

**完成标准**（回放语料）：复盘提出的新监控项进入下一轮采集计划；超过上限的进入建议；用户确认过的条目不被自动关闭；无依据的修订被拒绝。

## 7. P5 报告与前端

1. **报告**：今日动态与周报从已发布事件与栏目投影（复用 `digest`、`brief_analysis`）；历史论文/专利按原日期进入基线，不冒充当期新增。
2. **前端**（沿用现有页面与设计规范，不改导航）：
   - 项目顶部与任务页：更新进度（已收录 X 份；分析中 / 部分完成 / 已完成）。
   - "用已保存材料重新分析"按钮（分析失败或部分完成时）。
   - "当前判断"：投资假设列表（可编辑）；预警结论标明关联的假设。
   - 外部信息各页：确认相关与候选分开显示。
   - 监控范围页：沿用现有方案表与"待你确认的建议"，接入新复盘结果。
   - **删除**旧的"恢复请求""结果待核""刷新被阻止"等对话框与相关文案。
3. 每页在浏览器中实际查看，截图交你确认。

**确认节点**：逐页走查。

## 8. P6 切换与删除

1. "更新"、定时调度、新建项目全部只创建新任务类型；旧任务类型 `external` / `external_followup` 不再创建。
2. 删除设计文档第 6 节清单中的模块与对应测试、Node 工具桥；更新 `scripts/layer_map.json`。
3. 提交删除清单与剩余调用路径核对结果：新旧双派发为零，DSH 无调用方。
4. 文档：更新 `docs/developer-architecture.md` 为新架构。

**完成标准**：全量测试、Node 测试、前端构建、wheel 构建、全新安装冒烟全部通过；删除清单完成。

## 9. 里程碑验收

1. 完整审查：精确提交、改动范围、测试结果、未验证项。
2. 真实验收：在用户授权的小额预算内，对已有项目点一次"更新"、新建一个项目完整跑一轮；人为让分析失败一次，验证从快照恢复且采集调用为 0。
3. 通过后按既有安全流程更新本机：备份、停新派发、排空、切换、核对身份与哈希、保留回滚。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 回放语料覆盖不到新流水线发出的新请求（例如新增的确认名查询） | 回放未命中时明确报错并列出缺失请求；这部分留到真实验收，或用公开免费来源做一次有限录制（需你同意） |
| 直接调用的分析质量不如原智能体 | P4 用同一批回放材料对比旧分析结果；差距列入确认节点 |
| 侧向功能（竞品研究、行业格局等）依赖被删除的模块 | P6 前逐个核对调用关系；有依赖的先改为读新产物 |
| 旧数据结构不一致导致迁移出错 | 迁移只改任务状态；在备份副本上先跑并逐表比对 |
| 进度慢于预期 | 每个确认节点汇报实际进度；必要时把 P4b 的探索额度或部分前端顺延，不动里程碑两条结果 |
